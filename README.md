# Mini NPU Simulator

Python 3.8 이상에서 동작하며 외부 라이브러리가 필요하지 않습니다.

## 1. 실행 방법

`main.py`와 `data.json`을 같은 폴더에 두고 `python main.py`를 실행합니다.
메뉴 `1`은 3×3 필터 A/B와 패턴을 각각 세 줄씩 입력하는 모드입니다. 한 줄에는 공백으로 구분한 유한한 숫자 세 개를 입력합니다. 오류가 있는 줄은 재입력합니다.
메뉴 `2`는 같은 폴더의 `data.json`을 읽고 각 패턴을 검사합니다. 예제 JSON은 5×5, 13×13, 25×25 케이스 7개(정상 6개, 의도적 동점 1개)입니다. 실제 과제에서 제공된 `data.json`이 있다면 예제 파일을 교체하십시오.

## 2. JSON 구조

최상위 키는 `filters`와 `patterns`입니다. `filters`는 `size_5`, `size_13`, `size_25`를 키로 갖고, 각 크기별로 `cross`와 `x`라는 필터 배열을 담습니다. `patterns`는 `size_N_idx` 키마다 `input`(N×N 숫자 배열)과 `expected`(`+` 또는 `x`)를 담습니다. 필터 키의 `cross`와 expected의 `+`는 `Cross`로, `x`는 `X`로 정규화됩니다. `Cross`/`X` 자체도 허용합니다.

## 3. 구현 요약

`mac`은 이중 반복문에서 패턴과 필터의 같은 좌표 값을 곱해 누적합니다. 두 점수의 차이의 절댓값이 `1e-9`보다 작으면 `UNDECIDED`, 아니면 더 큰 점수의 라벨을 반환합니다. 비교 정책은 절대 허용오차이며 경계 `1e-9`는 동점에 포함되지 않습니다. 입력 데이터의 크기, 자료형, 숫자의 유한성, 라벨 및 필터 존재 여부를 검증합니다. 필터 그룹이 잘못되어도 해당 그룹을 참조하는 패턴은 개별 FAIL로 기록합니다.

## 4. 결과 리포트

1. 제공된 예제 데이터는 총 7개 패턴으로 구성됩니다.
2. 6개는 Cross 또는 X 필터와 동일한 패턴이므로 해당 라벨로 판정되어 PASS가 예상됩니다.
3. `size_13_3`은 모든 원소가 0이어서 두 필터의 MAC 점수가 모두 0입니다.
4. 따라서 `size_13_3`은 `UNDECIDED`로 판정되며 expected `X`와 달라 FAIL이 예상됩니다.
5. 예제의 예상 집계는 전체 7개, PASS 6개, FAIL 1개입니다.
6. 실제 과제의 원본 `data.json`은 제공되지 않았으므로 그 파일에 대한 결과는 별도 실행으로 확인해야 합니다.
7. 라벨 정규화가 없다면 expected `+`와 예측 `Cross`가 다르게 비교되어 잘못된 FAIL이 발생할 수 있습니다.
8. 필터 키 `cross`를 `Cross`로 바꾸는 것도 같은 의미의 라벨을 일관되게 처리하기 위해 필요합니다.
9. 행·열 개수 불일치, 숫자 이외의 값, 누락된 필터, 잘못된 키는 데이터/스키마 문제로 분류합니다.
10. 정상적인 스키마인데 예상과 다른 라벨이 나오면 입력 패턴과 필터 내용, 예상 라벨 및 MAC 판정 로직을 점검합니다.
11. 두 점수가 거의 같은 경우에는 부동소수점 반올림 오차가 판정을 뒤집을 수 있습니다.
12. 절대 허용오차 `epsilon=1e-9`는 이런 작은 차이를 동점으로 처리해 불안정한 판정을 줄입니다.
13. 다만 epsilon으로 인한 `UNDECIDED`는 expected가 Cross 또는 X라면 FAIL이며, 임의로 PASS로 바꾸지 않습니다.
14. 성능 표의 시간은 파일 읽기나 출력이 아닌 MAC 함수 호출만을 10회 측정한 평균입니다.
15. 측정 단위는 ms이며 실행 장치, Python 버전, 운영체제 부하에 따라 달라집니다.
16. MAC의 각 원소에 대해 곱셈 1회와 누적 덧셈 1회가 수행되므로 반복 횟수는 N²입니다.
17. 3×3, 5×5, 13×13, 25×25의 원소별 연산 횟수는 각각 9, 25, 169, 625입니다.
18. 따라서 단일 MAC 함수의 시간 복잡도는 **O(N²)**이며, 추가 누적 변수의 공간 복잡도는 **O(1)**입니다(입력 배열 저장 공간 제외).
19. 두 필터를 평가하면 약 2N²번의 원소별 연산이 필요하지만 상수 배수이므로 전체 시간 복잡도 역시 O(N²)입니다.
20. 작은 입력에서는 함수 호출 및 타이머 오버헤드 때문에 실제 측정 시간이 N²에 정확히 비례하지 않을 수 있습니다.
21. 모든 케이스가 PASS인 데이터에서는 정규화, 스키마 검증, 점수 비교 정책이 주어진 expected와 일치한 것으로 해석할 수 있지만, 프로그램 전체의 무오류를 보증하지는 않습니다.

## 5. 대규모 입력에서의 시간 및 메모리 문제와 최적화 방안

### 5.1 대규모 MAC 연산의 한계

본 프로그램은 N×N 크기의 패턴과 필터를 입력받아 각 위치의 원소를 곱하고 누적하는 MAC 연산을 수행한다.

MAC 연산의 시간 복잡도는 O(N²)이며, 입력 크기가 증가하면 연산량도 제곱에 비례하여 증가한다.

예를 들어 다음과 같다.

| 입력 크기 | MAC 연산 횟수 |
|---|---:|
| 3×3 | 9 |
| 25×25 | 625 |
| 100×100 | 10,000 |
| 1000×1000 | 1,000,000 |

1000×1000 입력에서는 필터 하나당 100만 번의 곱셈 및 누적 연산이 필요하다. 두 필터를 비교하면 총 200만 번의 MAC 연산이 수행된다.

특히 Python의 반복문은 인터프리터 수준의 실행 비용이 발생하므로 대규모 입력에서 실행 시간이 증가할 수 있다.

메모리 측면에서도 문제가 발생할 수 있다. 1000×1000 행렬은 100만 개의 원소를 포함하며, 각 원소를 8바이트 부동소수점 값으로 저장한다고 가정하면 행렬 하나에 약 8MB의 데이터가 필요하다.

다만 실제 Python의 중첩 리스트는 리스트와 객체의 추가 메모리 비용이 발생하므로 이보다 많은 메모리를 사용할 수 있다.

### 5.2 블록 및 타일 기반 처리

대규모 행렬을 한 번에 처리하는 대신 일정한 크기의 블록으로 나누어 계산하는 방법을 고려할 수 있다.

예를 들어 1000×1000 행렬을 100×100 크기의 타일 100개로 나누어 처리할 수 있다.

각 타일에서 MAC 연산을 수행한 후 부분합을 전체 점수에 누적하면 최종 결과를 계산할 수 있다.

이 방법은 전체 연산량 O(N²)을 감소시키지는 않지만, 데이터 접근의 지역성을 개선하여 캐시 효율을 높일 가능성이 있다.

단, Python 반복문으로 단순히 블록을 나누는 것만으로는 오히려 반복문 오버헤드가 증가할 수 있으므로 실제 성능 측정을 통한 검증이 필요하다.

### 5.3 스트리밍 기반 처리

현재 프로그램은 전체 패턴과 필터를 메모리에 저장한 후 연산한다.

스트리밍 방식에서는 데이터를 행 단위 또는 블록 단위로 읽으면서 MAC 연산을 수행할 수 있다.

각 블록의 부분합만 유지하면 되므로 전체 입력 데이터를 동시에 메모리에 저장할 필요가 없다.

예를 들어 필터를 메모리에 유지하고 패턴을 한 행씩 읽어 처리하면 패턴 전체를 저장하는 메모리를 절약할 수 있다.

다만 JSON 파일을 `json.load()`로 한 번에 읽는 현재 구조는 완전한 스트리밍 방식이 아니다. 실제 스트리밍을 구현하려면 데이터 저장 형식이나 파싱 방식을 변경해야 한다.

### 5.4 병렬화 방안

MAC 연산은 각 원소의 곱셈을 독립적으로 계산할 수 있다는 특징이 있다.

따라서 여러 블록의 부분합을 동시에 계산한 후 최종적으로 합치는 병렬화가 가능하다.

Python 표준 라이브러리의 `multiprocessing`을 사용하면 여러 프로세스에서 블록을 분산 처리할 수 있다.

그러나 프로세스 생성, 데이터 전달 및 결과 병합에도 비용이 발생하므로 작은 입력에서는 병렬화가 오히려 비효율적일 수 있다.

또한 병렬 누적 순서가 달라지면 부동소수점 반올림 오차가 달라질 수 있으므로 epsilon 기반 비교 정책이 중요하다.

## 6. CPU와 NPU의 MAC 연산 병목 비교

### 6.1 CPU 기반 연산

본 프로그램은 Python 반복문을 이용하여 MAC 연산을 수행한다.

CPU는 범용적인 명령어 실행과 복잡한 제어 흐름에 적합하다. 그러나 현재 구현은 단일 실행 흐름에서 원소를 순차적으로 처리하므로 대규모 MAC 연산에서 처리 시간이 증가한다.

CPU 자체가 직렬 연산만 수행하는 것은 아니다. 멀티코어, SIMD 명령어, 벡터화 및 병렬 프로그래밍을 활용하면 여러 연산을 동시에 처리할 수 있다.

따라서 본 프로그램의 실행 결과는 CPU 하드웨어 전체의 성능이 아니라 Python 순차 구현의 성능을 나타낸다.

### 6.2 NPU 기반 연산

NPU(Neural Processing Unit)는 신경망에서 반복적으로 사용되는 행렬 연산과 MAC 연산을 효율적으로 수행하도록 설계된 전용 프로세서이다.

일반적으로 NPU는 다수의 연산 유닛을 활용하여 많은 곱셈 및 누적 연산을 병렬로 수행한다.

또한 데이터 재사용을 고려한 내부 메모리 구조와 연산 배열을 활용하여 데이터 이동 비용을 줄이도록 설계된다.

따라서 충분히 큰 연산에서는 높은 처리량과 전력 효율을 달성할 수 있다.

다만 실제 성능은 NPU 구조, 지원 정밀도, 메모리 대역폭 및 데이터 전송 비용에 따라 달라진다.

### 6.3 CPU와 NPU 비교

| 비교 항목 | CPU | NPU |
|---|---|---|
| 주요 목적 | 범용 연산 | 신경망 연산 가속 |
| 병렬 처리 | 멀티코어 및 SIMD 활용 | 다수의 MAC 유닛 활용 |
| MAC 처리 | 구현에 따라 순차·병렬 처리 | 대규모 병렬 처리에 최적화 |
| 주요 병목 | 명령어 처리, 메모리 접근 등 | 메모리 대역폭, 데이터 이동, 연산 유닛 활용률 등 |
| 작은 입력 | 실행 오버헤드가 상대적으로 작을 수 있음 | 데이터 전송 및 초기화 비용이 부담될 수 있음 |
| 대규모 입력 | 최적화 수준에 따라 성능 차이 발생 | 병렬성이 충분할 때 높은 처리량 기대 |

### 6.4 대규모 MAC 연산의 병목 분석

MAC 연산의 성능은 단순히 곱셈과 덧셈의 횟수만으로 결정되지 않는다.

메모리에서 데이터를 읽어오는 속도가 연산 처리 속도보다 느리면 메모리 대역폭이 병목이 될 수 있다.

또한 패턴과 필터를 반복해서 읽는 과정에서 캐시 적중률이 낮으면 성능이 저하될 수 있다.

NPU에서는 다수의 MAC 유닛이 동시에 연산하더라도 데이터를 충분히 빠르게 공급하지 못하면 연산 유닛이 대기하게 된다.

이러한 문제를 완화하기 위해 타일링, 데이터 재사용, 온칩 메모리 활용 등의 최적화 기법을 적용한다.

### 6.5 결론

본 프로젝트는 Python을 사용하여 MAC 연산의 기본 원리와 시간 복잡도를 확인하는 시뮬레이터이다.

1000×1000과 같은 대규모 입력에서는 연산량 증가와 메모리 접근 비용이 중요한 성능 문제가 된다.

블록 처리와 스트리밍은 메모리 사용 및 데이터 접근을 개선하는 방법이며, 병렬화는 여러 MAC 연산을 동시에 수행하여 실행 시간을 단축할 가능성이 있다.

CPU와 NPU의 주요 차이는 연산을 수행하는 하드웨어 구조와 병렬 처리 방식에 있다.

본 프로젝트에서는 실제 NPU 하드웨어를 사용하지 않았으므로 CPU와 NPU의 성능을 직접 측정하거나 비교하지 않았다. 대신 MAC 연산의 구조를 바탕으로 두 프로세서의 병목 특성을 이론적으로 분석하였다.
